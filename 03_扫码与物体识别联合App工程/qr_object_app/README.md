# 扫码与十类识别 App 2.1.12

更新：2026-10-06。QR模式支持触屏移动真实扫描框，固定初始位置在config.py配置；默认仍中央50%。扫码改用原生灰度1920×1440、ZBAR，切入后丢2个预热帧，读图超时2000毫秒；合法三码单帧即确认。默认ROI[480,360,960,720]，保留触屏移动、200毫秒仅显示暂留、任务筛选、9564模型及原UART协议。物体模式恢复RGB888及模型实际输入尺寸。

## 1. 怎么运行

1. MaixVision连接MaixCAM Pro，打开整个 `qr_object_app`，运行整个项目，不只传main.py。
2. 或安装上一级 `dist/maix-qr_object_switch-v2.1.12.zip`。App ID仍为 `qr_object_switch`，安装会替换同ID旧App；需要保留旧设备应用时先自行备份。
3. 默认扫码；`UART_ENABLED=True`。USER短按扫码→物体识别，再短按→扫码，电控接管后也允许；长按1.5秒退出。扫码成功不会自己跳物体模式，等USER短按或MCU请求。一次加载/推理不能被同步打断，退出视觉不是电机急停，须由电控独立停车。
4. 115200、8N1、共地、3.3V：A19/TX→MCU PD6/RX，MCU PD5/TX→A18/RX。实际引脚按板型核对。

只拉Git不会更新相机/MCU。不要混装旧1.1.0安装包、本版源码和未适配电控固件。

本轮2.1.12安装包包含当前本地源码及用户保留的物体字号2。旧dist安装包不自动更新；请运行完整新版项目或安装2.1.12，同时记录实际部署版本与源码提交。当前仅电脑验证，未部署MC、未上传云端。

电控接管后手动切模式会暂停本轮业务回传，避免把手动查看结果冒充任务结果；屏幕显示`MCU PAUSED: NEW REQUEST REQUIRED`。同号重试回失败ACK（实际模式、status=1），不会强行切回；MCU须发递增新请求号重新接管。现有电控收到失败ACK可能终止该阶段，需由电控重新开始请求；这不是无缝恢复，更不是电机急停。实车先从电控停车，再进行手动诊断。

## 独立测试：扫码后只选任务物体

1. 开机扫码；未扫码也能短按USER查看全部十类物体，再短按回扫码。
2. 第一帧解出合法三位码就锁定，不再要求连续3帧。每位只能1、2、3；空帧、非法码或同帧不同码冲突不确认。全部解码结果参与确认，`QR_MAX=1`只限制画框。
3. 确认后发送QR53并留在扫码。短按USER进入OBJECT：扫331后UART只选蓝球ID3、蓝靶ID7、圆柱ID1；支持全部27组合，每类取配对输入帧中置信度最高且框有效的一个。
4. USER手动物体模式默认显示全部十类信息，UART仍只发送已确认三任务。无任务发空目标包，缺目标发空目标包或剩余目标，不沿用漏检坐标。黑桶不混入独立三任务；电控task4/0持续选桶，通用60/OBJECT诊断仍选三任务加桶。模型双缓冲的首轮仅预热、不发物体业务。
5. USER返回QR立即清旧任务及确认计数；重新扫码后等下一次短按或MCU命令。加载模型失败留在原模式，可短按重试；长按退出。
6. 电控接管始终优先：60/QR即使三码确认也继续扫码回传，等待主控切阶段；63指定目标无需相机先扫到码。接管后的显示仍可观察其他类别，触屏选择不改变UART目标。ACK完整写出前仍不取图/发业务。
7. USER手动切到OBJECT，默认显示全部十类检测信息，不要求先确认二维码；启动参数为OBJECT时也一样。手动查看全部不等于向电控发送全部：未接管时UART按已确认任务筛选，未扫码发空目标包；接管后手动切换则暂停业务，等MCU新请求恢复。
8. QR模式的青色细框是实际扫码区域，不是已识别二维码的框。把完整二维码及周围白边放入框内；默认宽、高各50%，可触屏移动位置。细框按显示缩放补偿，屏幕上约1像素，OBJECT模式不显示。

任务位：第1位球色、第2位靶色、第3位人质形状。颜色1红/2绿/3蓝；形状1圆柱/2圆锥训练别名（圆台）/3腰鼓训练别名（扁圆）。只移植05的筛选语义，不移植ASCII协议或9302模型。

## 扫码框怎么移动／固定位置

1. 在QR模式，点击MC实体屏幕中想放置框中心的位置，框随下一张图移动；点黑边无效，靠边自动贴边，框不超出图像。点一次移动一次，不是拖动。MaixVision电脑鼠标点击不能代替实体触屏。
2. 移动的是传给find_qrcodes的真实ROI，不只是显示框。切模式/新扫码请求保留当前位置，退出重启恢复config.py；不会自动写配置文件。
3. 固定启动位置，改config.py下面三行，再运行完整项目。X越小越靠左，Y越小越靠上；均为0～1的图像比例。下面例子上移框：

```python
QR_ROI_CENTER_X = 0.50
QR_ROI_CENTER_Y = 0.35
QR_ROI_TOUCH_MOVE = True  # False禁止触摸移动，仅使用固定位置。
```

1920×1440、宽高各50%时，上面固定框为[480,144,960,720]；原Y=0.50为[480,360,960,720]。触摸移动后终端[QR ROI]打印实际中心比例，可抄到配置里保存。框碰到边缘时实际中心可能与点的位置不同。

4. QR_ROI_FRACTION=0.50是宽、高各一半，不是全画面面积的一半；面积为25%。如近处完整码放不进框，可适当增大，1.0扫描全图、无法移动。范围增大会增加处理量，是否降低FPS须实测；移动或扩大ROI不会增加原图像素、解决失焦。
5. 移动后清掉旧结果显示缓存，并重算未确认码的连续帧；已锁存任务不变，不用触屏重新选择电控任务。当前默认合法三码单帧确认，所有UART包格式保持不变。

## 与原07测试版对齐的参数

本轮已对齐第36档的采集与解码路径：1920×1440、FMT_GRAYSCALE直接采集、ZBAR、默认中央宽高各50%、切入QR丢2个预热帧、read(block=True, block_ms=2000)。不是先采彩色再转灰度解码；原始灰度图解码后才缩到屏幕尺寸、转RGB画彩色框，屏幕标题仍显示真实采集尺寸。采集背景变黑白属于正常变化。

单帧成功仍须满足电控契约：完整三位、每位1～3，同帧不能有冲突。原07任意字符串解出即成功，本版不会回传11等非法任务；合法码第一帧即锁存并发送53，后续消失仍发锁存码。单帧确认减少等待，也增加偶发合法误解码被锁定的风险；可将TASK_CONFIRM_FRAMES改回3，但当前按用户要求为1。

QR与OBJECT切换会关闭摄像头并按目标格式重开；失败尝试恢复旧尺寸/格式，恢复失败退出并提示重启，避免拿灰度帧给彩色模型。预热会增加切模式耗时，不改变请求、ACK或包字节；同号重试不重新打开相机。OBJECT仍RGB888、模型实际输入尺寸。相机接口依据：[Sipeed Camera API](https://wiki.sipeed.com/maixpy/api/maix/camera.html)。

触屏移动真实ROI功能保留。完整码与白边要在框内；移动/扩大框不能解决失焦。没有调整曝光、焦距或新增图像增强。电脑测试只证明逻辑及参数一致，不能证明与07同样的实机远近范围；须同一纸码、光照、距离复测，记录原始MC图、实际尺寸及[QR]/[TASK]，不能用手机拍屏代替输入质量。

## 画框防闪烁与实际循环

配置`OBJECT_BOX_HOLD_MS = 200`表示：本帧检测到立即更新框与信息；某个物体漏检时，从它最后命中算起最多保留200毫秒，到期且仍漏检才消失。单位是毫秒，不是帧数；设0恢复漏检立即消失。没有sleep、没有固定200毫秒刷新间隔，也没有给整个推理循环加等待。只能在每轮推理结束后刷新屏幕，不能保证在阻塞推理中途准时擦框。

暂留的信息前加`HOLD`，位置、分数是最近命中时的值，不代表当前帧仍检测到。每个物体独立计时；连续命中立即更新位置，不会冻结框。新任务、成功切模式或实际图幅变化清空缓存，同号请求重试保留。短时漏检不会清掉触摸开关；缓存从画面消失后清掉开关。快速运动/同类交叉可能短时留下旧位置框，这是显示暂留，不是物体跟踪。

按用户最新要求：`QR_CAMERA_BUFFERS=1`，扫码单采集缓冲；`OBJECT_CAMERA_BUFFERS=2`、`DUAL_BUFFER=True`，物体识别使用相机双缓冲及模型CPU/NPU流水线。QR是CPU解码，不调用模型，不存在“扫码NPU双缓冲”。相机库原默认3缓冲也已具备缓冲能力，显式改成2并不保证比原版更快；实际FPS、延迟和内存须上板测量。依据：[Camera API](https://wiki.sipeed.com/maixpy/api/maix/camera.html)。

OBJECT每轮提交当前未绘制图，取得上次输入的结果；`frame_pair.py`保留一张独立`copy()`原图及采集时间，用上一帧原图绘制并回传其坐标。不会把上一帧结果套在当前画面上。新请求（同为OBJECT也算）、成功切模式清空配对，首轮丢弃可能属于旧任务的返回值，不画检测框、不发物体业务；第二轮才开始本任务结果。相同请求重试保留流水线。画框仅发生在推理提交后，不污染后续输入。依据：[双缓冲说明](https://wiki.sipeed.com/maixpy/doc/zh/vision/dual_buff.html)、[Image.copy API](https://wiki.sipeed.com/maixpy/api/maix/image.html)。

`cap`属于被识别原图的采集调用；`work`是本次detect调用耗时，不等于完整NPU推理延迟；01包的`vision_ms`从被识别原图采集循环起点到结果可用，包含约一帧流水线等待。不保证返回结果对应调用当下最新画面。一个配对帧的漏检结果发空包，不从200毫秒HOLD显示缓存取坐标；HOLD不提高识别率或FPS。双缓冲提高吞吐的同时引入结果延迟并增加内存，需控制侧实测可接受性。

## 触屏逐个开关物体信息

1. 自动扫码任务/电控任务中，任务目标信息默认显示，其他物体信息默认隐藏。全部检测框和中心十字都保留；在MC实体屏幕点其他框显示信息，再点隐藏；点任务目标隐藏信息，再点恢复。多个物体分别记开关，不互相替换。
2. USER手动进入OBJECT默认显示所有检测信息，也可以逐个点击隐藏/显示。点图像内空白处清除开关、恢复当前模式默认值（任务模式显示任务目标，手动模式显示全部）；图像外黑边不操作。MaixVision电脑预览鼠标点击不等于MC触屏操作。
3. 信息含类别、置信度、中心X/Y；有触摸开关时增加框宽w、高h。坐标/尺寸单位为源图像素。连续帧以同类别和框重叠关联各物体；本帧未命中的框暂留时标记HOLD。缓存到期从画面消失后清除开关，再出现按当前模式默认显示；多个同类交叉/快速移动不保证身份跟踪。
4. 新电控请求或USER成功切模式时清除开关；同号重试保留。触摸只影响画面，不改变电控任务、阈值和UART目标，隐藏任务目标也继续发送本帧坐标。黑桶任务没找到仍发空目标包。
5. 标签含底色一起避让，空间不足最多缩小3次；仍放不下时保留框和中心十字、省略该框文字。可以点击其他框隐藏信息，减少文字占用。
6. 缺少触屏API/驱动异常时打印`[TOUCH] disabled`或`read failed`，恢复当前模式默认显示，检测和串口继续。事件非阻塞、每轮最多8条，长按不反复开关；退出时释放触屏。

坐标映射依据[Sipeed TouchScreen API](https://wiki.sipeed.com/maixpy/api/maix/touchscreen.html)和[Display FIT_CONTAIN规则](https://wiki.sipeed.com/maixpy/api/maix/display.html)：小图居中不放大，大图等比缩小。设备实际显示方向、触屏与字体观感仍需上板确认。

## 2. 运行流程

1. 电控发60/QR，视觉回ACK后扫码；第一帧合法三位1..3任务码即确认并锁存。
2. 视觉通过53回三码。码消失后继续回锁存值；新QR请求才清空，同号重试不清空。
3. 电控依次发63：**球task1→桶task4→靶task2→人质task3**，每次换请求号。63自动进入OBJECT，每帧只发指定类别最高分一个，没找到发空帧。
4. 黑桶task4/digit0每帧持续发ID9，不缓存丢失桶坐标。球/靶/人质阶段不附带桶；画面可显示其他类别。
5. 当前电控阶段结束仅关闭本地业务接收，不要求视觉停止；下一阶段换请求号。可选60/IDLE仍停止取图、推理和业务结果。视觉不控制电机或猜抓球是否完成。

| 请求 | digit1 | digit2 | digit3 |
| --- | --- | --- | --- |
| task1球 | 红球ID4 | 绿球ID5 | 蓝球ID3 |
| task2靶 | 红靶ID6 | 绿靶ID8 | 蓝靶ID7 |
| task3人质 | 圆柱ID1 | 圆锥ID2 | 腰鼓ID0 |

桶只接受task4/digit0→ID9。digit是数值字节，不是ASCII。例QR123：球4→桶9→靶8→人质0。

通用60/OBJECT保留33诊断的“三任务加桶”，不是四阶段请求。未扫QR时只选桶。相同类别取最高置信度，同分先出现者；每帧重选，不跟踪或沿用旧框。

## 3. 配置和数据

- `MODEL_FILE=model_9564.mud`，对应9564.cvimodel，模型不变。`config.py`中`OBJECT_TEXT_SCALE=2`控制物体标签，`BOX_TEXT_SCALE=2`保留扫码字号；按屏幕尺寸补偿源图缩小。十类框/中心十字/标签底色同类同色，标签用黑色实心字，避免细线字与框混在一起。坐标宽度不够时分x/y两行，QR三码/颜色/形状分行，长行或拥挤布局会缩字防出界；物体文字含底色统一避让。旧9541/9302保留但不运行、不打入包。
- 类别顺序：0扁圆物体/本项目腰鼓，1圆柱，2圆台/本项目圆锥，3蓝球，4红球，5绿球，6红靶，7蓝靶，8绿靶，9黑桶。训练别名须实物核验。
- 阈值0.35；OBJECT用模型实际画幅，不猜480×320；QR1920×1440，中心区域扫码。相机固件返回的实际尺寸及联合模式切换速度仍需上板确认。
- 目标01发ID、置信度×1000、中心X/Y、框宽高、真实画幅及处理耗时。靶也保留旧字段，电控业务可只消费X。坐标像素、左上原点，不是毫米。
- QR53只含seq、count、三个ASCII数字（有码）；无字符串长度、无二维码位置/大小。未扫码count0。
- 外层62绑定request_id；ACK61全写后才能取新图/发结果。UART短写只续未写尾部，失败暂停待ACK业务。

详细字节字段、CRC、固定向量及电控适配要求见 [VISION_TO_CONTROL.md 第4～5节](../../VISION_TO_CONTROL.md)。不支持的二维码格式不能靠补零框假装兼容。

终端RX打印原始HEX；ACK完整日志；业务HEX默认每10帧。`[PERF] sent_ids`是筛入发送包的ID；`[UART TX] complete`仅证明本机write全长，**不证明MCU收到或接受**。

## MC自动日志：只需运行新版工程

1. 运行整个新版`qr_object_app`，不能只运行main.py；`uart_log.py`必须随工程上传。
2. DEVICE出现`[UART FILE] saving /root/vision_uart_logs/uart_..._001.txt`即说明日志已创建。IDLE也会记录收到的请求和ACK，不需按USER开启记录。
3. 做同一轮33静止诊断。测试后正常停止App，等待日志收尾，**不要直接断电**。
4. 在MaixVision的**设备文件管理器**进入`/root/vision_uart_logs`并刷新。每次启动有独立前缀；下载该轮所有`_001.txt/_002.txt/...`。或者告诉Codex设备IP和合法SSH登录，由Codex直接下载。
5. 电控端仍需同一轮手机BLE导出文件。MC只能证明自身UART调用，不能代替MCU接收器内部状态。取回两端日志后再审查、分析并上传云端；设备程序不会自己向GitHub发日志。

文件每条带UTC时间与本机单调毫秒，含App版本、UART配置、模型名、RX完整HEX、每次WRITE驱动报告的实际片段以及TX整帧意图/写入状态。文件**不按每10帧采样**；控制台采样设置不影响本机文件。WRITE返回负值/异常不能确定额外字节是否已上线路，不能误作对端接收确认。

后台写入，有界256条队列，约0.5秒flush；队列满时丢日志但不中断串口，并记录`[LOG GAP]`。每片1MiB、每轮16MiB、目录64MiB；达到限额或磁盘失败就停止日志并提示，识别与通信继续。**不会删除旧日志**，下载后由用户清理。突然断电/强杀可能丢掉队列、缓存或文件系统尚未持久化的尾部，不能保证完整；日志缺失不等于UART丢包。

路径为MC持久目录，不是会被下次运行替换的`/tmp/maixpy_run`。文件管理方式见[Sipeed官方MaixVision说明](https://wiki.sipeed.com/maixpy/doc/zh/basic/maixvision.html#传输文件到设备)。
